# 调试状态查询与启动链路设计

- **日期**：2026-08-18
- **状态**：已实现并验证
- **范围**：`get_debug_state` 工具、`availableDebugTargets`、`.code-workspace` 配置启动修复、`start_debugging` 异步返回、`stop_debugging` 路由提示与进程终止、重复启动拦截、`restart_debugging` 路由提示与重启实现

## 1. 背景与动机

DebugMCP 通过 DAP 控制 VS Code 调试器，为 AI 智能体提供 17 个调试控制工具。但在实际使用中存在四个缺口：

1. **缺少只读状态查询入口**：智能体调试前/中需要确认"当前是否在调试、停在哪、有哪些断点"，但现有工具要么会改变调试器状态（step/continue/pause），要么只能查断点（`list_breakpoints`）。
2. **多根工作区配置无法启动**：调试配置可定义在 `.code-workspace` 文件的 `launch` 段（而非 `.vscode/launch.json`），通过 `vscode.debug.startDebugging(folder, configName)` 按名查找时会被 VS Code 拒绝。
3. **长运行应用导致 MCP 调用超时**：`start_debugging` 会阻塞等待会话"停在断点"或"超时"，对 Spring Boot 等服务型应用（可能长时间运行、不触发断点）会超过 MCP 客户端请求超时（`-32001`）。
4. **窗口重载后路由缓存丢失**：MCP 连接重置会清空 per-session 路由缓存，原本 hint-less 的工具（`stop_debugging` 等）即使调试会话仍在运行，也会报 `no active debug target`。

## 2. 需求

1. 新增 `get_debug_state` 工具：只读查询当前调试会话状态，不改变调试器。
2. `get_debug_state` 同时返回**可启动目标**列表（`availableDebugTargets`），覆盖 `.code-workspace` 与 `launch.json` 两种配置来源。
3. 支持从 `.code-workspace` 定义的工作区级配置启动调试。
4. `start_debugging` 改为**异步启动语义**：启动命令成功发出即返回，后续通过 `get_debug_state` 与 Debug Console 确认。
5. `stop_debugging` 支持可选路径提示（解决重载后路由缓存丢失），并在 `integratedTerminal` 模式下主动终止被调试进程。
6. **防止重复启动**：已有活跃会话时 `start_debugging` 直接拦截并报错。
7. `restart_debugging` 支持可选路径提示，并在重启时终止旧进程、用原配置重新启动（`integratedTerminal` 下不依赖 VS Code 原生 restart）。

## 3. 设计

### 3.1 `get_debug_state` 工具

**定位**：纯只读的会话状态概览，智能体在任何时刻调用均安全。

**参数**：
- `fileFullPath`（可选）：多窗口路由模式的路径提示；已建立会话时可省略以复用缓存目标。

**返回结构**（基于 `DebugState.toString()` 扩展）：

```json
{
  "sessionActive": false,
  "availableDebugTargets": []
}
```

- `sessionActive` 恒返回；
- 会话活跃时附带 `configurationName`、`stackTrace`（`"函数名:行号"` 数组）、`breakpoints`（`"文件:行 [when: 条件]"` 数组）、`fileFullPath`、`fileName`、`currentLine`、`currentLineContent`、`nextLines`、`frameId`、`threadId`、`frameName`；
- 无活动会话时仅返回 `{"sessionActive": false}`（不抛错）。

**实现**：`DebuggingHandler.handleGetDebugState()` 解析 `getCurrentDebugState()` 的 JSON，附加 `availableDebugTargets` 后返回。路由层与 `add_breakpoint` 模式一致：可选 path hint 转发至目标窗口。

### 3.2 `availableDebugTargets`（可启动目标）

**设计要点**：目标是"运行和调试下拉框"会展示的静态配置，来源有三类：

| source | 来源 | 读取方式 |
|--------|------|---------|
| `workspace` | 单根 `.vscode/launch.json` 或 `.code-workspace` 的 `launch` 段 | `workspace.getConfiguration('launch')`（工作区级） |
| `folder` | 多根工作区中各文件夹的 `.vscode/launch.json` | 遍历 `workspaceFolders` 的 `getConfiguration('launch', folder.uri)` |
| `default` | DebugMCP 按文件扩展名自动生成的启动配置 | `LANGUAGE_MAP` 去重后的 debuggerTypes |

**关键实现**：用 VS Code 工作区配置 API（自动合并 `.code-workspace`），**不直接解析 launch.json 文件**。按配置名去重（`Set`）。`default` 条目附带全部支持的调试器类型，供智能体按语言判断。

### 3.3 `.code-workspace` 配置启动修复

**问题**：`get_debug_state` 能列出 `.code-workspace` 配置，但 `start_debugging(configurationName)` 报"`launch.json` 中缺少配置"。

**根因**：`vscode.debug.startDebugging(folder, configName)` 传入具体 folder 时，VS Code 只在**该 folder 的 `launch.json`** 中按名解析；`.code-workspace` 的 `launch` 段是**工作区级**配置，无法命中。

**修复**：`getDebugConfig` 对命名配置先查工作区级配置（`getConfiguration('launch').get('configurations')`），命中则返回**配置对象**（浅拷贝），`startDebugging(folder, configObject)` 直接用对象启动（不再按名查找）；未命中则保持返回配置名字符串，让 VS Code 解析 folder 级/动态 provider 配置。`${workspaceFolder:xxx}` 显式命名的变量由 VS Code 正常解析。

### 3.4 `start_debugging` 异步返回

**问题**：原实现等待 `waitForDebugSessionReady` 的四种状态（`stopped`/`terminated`/`no-session`/`timeout`），对长运行应用必须等满 `timeoutInSeconds`（默认 180~300s）才返回 `timeout` 分支，超过 MCP 客户端请求超时。

**设计决策**：启动命令成功发出（`startDebugging` 返回 `true`）即返回：

```
Debug session start command issued for: <file> using configuration '<name>'.
The application is launching asynchronously. Use get_debug_state to check whether
the session is active and where execution is paused, and consult the Debug Console
for logs.
```

- 不再 `waitForDebugSessionReady`、不再与 `runComplete` race；
- testName 路径（Testing API）同样 await dispatch 成功后立即返回；
- 启动失败（`started === false`）或配置解析失败（如 .NET 未构建）仍立即抛错。

**确认链路**（异步启动后）：`get_debug_state` 查会话活跃与暂停位置 → Debug Console 查启动日志。

### 3.5 `stop_debugging` 路由提示与进程终止

**问题 1（路由）**：窗口重载后 MCP 连接重置，per-session 路由缓存清空，hint-less 的 `stop_debugging` 报 `no active debug target`，即使会话仍在运行。

**修复 1**：`stop_debugging` 增加可选 `fileFullPath` 参数（与 `get_debug_state`/`add_breakpoint` 模式一致），无缓存 target 时按路径定位窗口。`get_debug_state` 已验证：带路径调用可路由到目标窗口。

**问题 2（进程残留）**：`console: integratedTerminal` 下，被调试进程属于终端 shell 而非调试适配器，java-debug 停止调试时**不会终止 JVM**（实测确认：`terminateDebuggee: true` 配置无效，UI/API 停止均不终止）。`internalConsole` 虽能终止进程，但输出在调试控制台而非集成终端，不满足"终端看输出 + 停止终止进程"的双重诉求。

**修复 2**：`DebuggingExecutor.stopDebugging` 在停止会话后，向运行 debuggee 的集成终端发送 **`Ctrl+C`**（`interruptDebuggeeTerminals`），终止残留进程。终端识别规则：

| 匹配规则 | 依据 |
|---------|------|
| 名称以 `Debug:` / `Run:` 开头 | java-debug 终端命名惯例（`JavaTerminalLinkProvder`） |
| 名称等于会话配置名 | VS Code 调试集成终端默认命名 |

**设计取舍**：主动中断终端进程存在极小的误杀风险（仅限匹配的调试类终端），换取"终端看输出 + 停止终止进程"的完整闭环，收益大于风险。

### 3.6 重复启动拦截

**问题**：已有一个活跃会话时再次 `start_debugging` 同一配置，VS Code 接受命令并可能创建多实例（多实例可能端口冲突；`stop_debugging` 只能停 `activeDebugSession`，导致遗留进程）。

**设计决策**：`handleStartDebugging` 开头检查 `hasActiveSession()`，存在活跃会话时**拦截并抛错**：

```
A debug session is already active. Stop it first with stop_debugging before starting a new one.
```

智能体应先 `stop_debugging` 再重新启动，保证启停语义清晰、无遗留进程。

### 3.7 `restart_debugging` 路由提示与重启实现

**P1（路由）**：`restart_debugging` 增加可选 `fileFullPath` 参数（与 `stop_debugging` 一致），解决窗口重载后路由缓存丢失问题。

**P2（重启实现）**：`workbench.action.debug.restart` 在 `integratedTerminal` 下不可靠——复用终端启动新 debuggee 时报 `JDI TransportTimeoutException`。改为 **stop + start 组合**：

```
stopDebugging(session)           ← 停止会话 + Ctrl+C 中断终端（终止旧 JVM）
→ 等待 3s（旧进程完全退出）        ← 防端口/传输冲突
→ startDebugging(undefined, session.configuration)  ← 用原配置重启
```

**P3（异步语义）**：返回 "restart command issued ... use get_debug_state"，去掉固定等待，与 `start_debugging` 一致。

**实测**：启动 → restart → 旧进程终止、新进程启动（PID 变化）、8080 无端口冲突、新会话活跃。

### 3.8 Agent Selection Popup 支持扩展（Qoder / CodeBuddy / Trae）

**问题**：安装后弹出的 Agent Selection Popup（`AgentConfigurationManager.getSupportedAgents`）只支持 7 个助手，缺少国内主流 AI IDE。

**新增助手**（配置路径经本地实测 + 官方文档确认）：

| 助手 | 配置路径 | 格式 / 字段 |
|------|---------|------------|
| Qoder | `~/.qoder/mcp.json` | JSON / `mcpServers` |
| CodeBuddy | `~/.codebuddy/mcp.json` | JSON / `mcpServers` |
| Trae | `%APPDATA%\TraeCN\User\mcp.json` | JSON / `mcpServers` |

**CodeBuddy `type` 特判**：CodeBuddy 的 MCP 配置仅支持 `stdio` / `sse` / `http`，**不识别 `streamableHttp`**（其余助手默认生成 `streamableHttp`）。因此：
- `getDebugMCPConfig` 对 CodeBuddy 返回 `type: "http"`；
- `migrateExistingConfigurations` 将 CodeBuddy 与 Copilot CLI 归入"http 组"，避免把 `http` 误迁移为 `streamableHttp`；
- `MCPServerConfig` 接口补充可选 `description` 字段（匹配 CodeBuddy 现有配置格式）。

**说明**：Qoder 文档确认其可自动识别 Streamable HTTP URL（无需特判）；Trae 支持标准传输。CodeBuddy 官方推荐路径为 `~/.codebuddy/.mcp.json`，但 `mcp.json` 仍兼容（用户本地既有文件即 `mcp.json`，按用户确认写入）。

## 5. 数据流

### `get_debug_state`

```
Agent ── MCP HTTP ──▶ DebugMCPServer ──▶ RoutingDebuggingHandler
       ◀── 状态 JSON ──┴─(path hint 定位窗口 / 复用缓存 target)──▶ ControlServer
                                                                      ▼
                                                            DebuggingHandler.handleGetDebugState()
                                                                      ▼
                                                   getCurrentDebugState() + getAvailableDebugTargets()
```

### `start_debugging`（异步 + 拦截）

```
Agent ── MCP ──▶ DebugMCPServer ──▶ RoutingDebuggingHandler ──▶ ControlServer
                                                                      ▼
                                                    hasActiveSession()？──是──▶ 抛错（重复启动拦截）
                                                                      ▼ 否
                                                   getDebugConfig()（工作区级→配置对象）
                                                                      ▼
                                          vscode.debug.startDebugging(folder, configObject)
                                                                      ▼
                                                    立即返回 "start command issued"
```

### `stop_debugging`（停止 + 终止进程）

```
Agent ── MCP ──▶ DebugMCPServer ──▶ RoutingDebuggingHandler ──▶ ControlServer
                                                                      ▼
                                                   vscode.debug.stopDebugging(activeSession)
                                                                      ▼
                                          interruptDebuggeeTerminals(sessionName)
                                          （向 "Debug:"/"Run:"/配置名 终端发 Ctrl+C）
                                                                      ▼
                                                      返回 "stopped successfully"
```

### `restart_debugging`（stop + start 组合）

```
Agent ── MCP ──▶ DebugMCPServer ──▶ RoutingDebuggingHandler ──▶ ControlServer
                                                                      ▼
                                                          stopDebugging(session)
                                                          （含 Ctrl+C 中断旧 JVM）
                                                                      ▼
                                                          等待 3s（旧进程完全退出）
                                                                      ▼
                                            startDebugging(undefined, session.configuration)
                                                                      ▼
                                                      返回 "restart command issued"
```

## 6. 错误处理与边界

| 场景 | 行为 |
|------|------|
| 多窗口路由无缓存目标、未传 path hint | 返回 `no active debug target` 提示（与现有 hint-less 工具一致） |
| 无活动会话 | `get_debug_state` 返回 `{"sessionActive": false}`；`stop_debugging` 返回 `No active debug session to stop`，均不抛错 |
| 命名配置不存在 | workspace 级未命中 → 走原名字符串路径，由 VS Code 报错；或使用默认配置 |
| **重复启动（已有活跃会话）** | **拦截抛错**，要求先 `stop_debugging` |
| 启动命令被拒绝（`started=false`） | 立即抛 `Failed to start debug session` |
| 配置解析失败（如 .NET 未构建） | 抛原配置错误（含修复提示） |
| 配置去重 | 同名配置以 `Set` 去重，避免多来源重复展示 |
| `integratedTerminal` 下停止后进程残留 | `stop_debugging` 发送 `Ctrl+C` 终止；极小概率误中断匹配终端 |
| 无活动会话时 `restart_debugging` | 抛 `No active debug session to restart` |
| `workbench.action.debug.restart` 在集成终端下失败（JDI 超时） | 已规避：restart 采用 stop+start 组合，不依赖该命令 |

## 7. 测试与验证

- `npm run check-types` / `npm run lint`：通过。
- `npm test`：**127 passing**；唯一失败为 pre-existing 的 `LAN exposure` 环境用例（本机网络允许经内网 IP 连 loopback 端口，与本次改动无关）。
- 实测（CodeBuddyDonghua + `local-thingsboard-ext.code-workspace`）：
  - `get_debug_state` 返回 `availableDebugTargets`，正确识别 `.code-workspace` 中的 `ThingsBoard + Qianmo Ext`、`ThingsBoard + Qianmo Ext - Install`（source=`workspace`）；
  - `start_debugging(configurationName='ThingsBoard + Qianmo Ext')` 异步快速返回，会话正常建立（`sessionActive=true`）；
  - 完整启停闭环（10 步）：无会话停止幂等 → 异步启动 → 会话活跃 → 重复启动被拦截 → 停止成功 → 重复停止幂等 → 最终 `sessionActive=false`；
  - `console: internalConsole` 下停止调试 → **JVM 进程终止 + 8080 释放**（已实测验证）；
  - `console: integratedTerminal` + `terminateDebuggee: true` → **无效**（JVM 仍残留，java-debug 固有问题），最终以 DebugMCP `Ctrl+C` 中断方案解决；
  - `restart_debugging` 完整闭环：启动（PID A）→ restart → 旧进程终止、新进程启动（PID B，8080 无端口冲突）→ 新会话活跃 → 停止 → 无进程残留 + 8080 释放。

## 8. 未纳入的设计（YAGNI）

- `get_server_status`（服务器/窗口注册状态查询）：多窗口诊断场景暂不需要，未实现。
- `compounds` 复合配置与扩展动态 provider 配置的展示：静态 `configurations` 已覆盖需求。
- `get_debug_state` 返回值中 `availableDebugTargets` 与状态分离展示：保持单一 JSON 结构，避免过度设计。
- 依赖 `terminateDebuggee` 配置终止进程：实测在 `integratedTerminal` 下无效，改为 DebugMCP 主动中断终端进程。
- 依赖 `workbench.action.debug.restart`：在 `integratedTerminal` 下复用终端启动新 debuggee 会 JDI 超时，restart 改用 stop+start 组合。
